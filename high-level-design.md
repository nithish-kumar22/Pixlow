## 1. Overall System Architecture

### Architectural Style: Layered + Event-Driven Hybrid

The platform follows a **5-layer architecture** where each layer has a single, well-defined responsibility. Layers communicate strictly downward (with events allowed to bubble upward for real-time updates).

```
┌─────────────────────────────────────────────────────────────────┐
│  LAYER 1 — PRESENTATION LAYER                                   │
│  Next.js SPA: Prompt UI, Canvas Editor, Code Editor, Preview    │
├─────────────────────────────────────────────────────────────────┤
│  LAYER 2 — API GATEWAY LAYER                                    │
│  tRPC / REST: Auth, Rate Limiting, Request Routing, SSE/WS      │
├─────────────────────────────────────────────────────────────────┤
│  LAYER 3 — SERVICE LAYER (Core Business Logic)                  │
│  Prompt Engine · Code Gen · Design Engine · Code Emit · Preview │
├─────────────────────────────────────────────────────────────────┤
│  LAYER 4 — ASYNC WORKER LAYER                                   │
│  BullMQ Workers: LLM Jobs, Compilation Jobs, Export Jobs        │
├─────────────────────────────────────────────────────────────────┤
│  LAYER 5 — DATA LAYER                                           │
│  PostgreSQL · Redis · S3/R2 · pgvector                          │
└─────────────────────────────────────────────────────────────────┘
```

### Why This Architecture?

| Decision | Reasoning |
|---|---|
| **Layered separation** | Each layer is independently testable, deployable, and scalable |
| **Async worker layer** | LLM calls take 5–30s; synchronous HTTP would time out and block threads |
| **IR as shared state** | The Intermediate Representation decouples the AI and canvas from the code editor; canvas/AI are the source of truth, code is emitted one-way (canvas → code) |
| **Event-driven updates** | Workers emit progress events over Server-Sent Events (SSE) back to the client for streaming UX |
| **Client-side bundler (Sandpack)** | Eliminates an entire category of server infrastructure for live preview |

### The Intermediate Representation (IR) — The Architectural Backbone

The IR is the most critical design decision in this system. It is a **versioned, schema-validated JSON document** that fully describes a mobile application's UI tree, styles, navigation, and event bindings.

```json
{
  "version": "1.0",
  "appId": "uuid",
  "screens": [
    {
      "id": "screen_home",
      "name": "Home",
      "layout": {
        "type": "View",
        "style": { "flex": 1, "backgroundColor": "#fff" },
        "children": [
          {
            "id": "comp_001",
            "type": "Text",
            "props": { "content": "Hello World" },
            "style": { "fontSize": 24, "fontWeight": "bold" },
            "events": { "onPress": { "action": "navigate", "target": "screen_detail" } }
          }
        ]
      }
    }
  ],
  "navigation": { "type": "stack", "initialScreen": "screen_home" },
  "theme": { "primaryColor": "#6366f1", "fontFamily": "Inter" },
  "dataBindings": {},
  "assets": []
}
```

The LLM and the canvas write this IR; the code editor displays code **generated from** the IR (one-way). The IR is **never generated by direct LLM → code**; the LLM only produces valid IR JSON. Code edits do not sync back to the canvas.

## 3. Key Modules

### 3.1 Prompt Processing Engine

**Purpose:** Transform raw, ambiguous natural language into a validated, enriched prompt that produces consistent LLM output.

#### Internal Pipeline

```
Raw User Prompt
      │
      ▼
┌─────────────────────────────────────────────────────┐
│  STEP 1: INPUT VALIDATION                           │
│  - Length check (min 10 chars, max 4000 chars)      │
│  - Content moderation (OpenAI moderation API)       │
│  - Language detection & translation to English      │
└────────────────────────────┬────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────┐
│  STEP 2: INTENT CLASSIFICATION                      │
│  - "What kind of app?" classifier (fast LLM call)   │
│  - Categories: e-commerce, social, productivity,    │
│    dashboard, game, utility                         │
│  - Outputs: { appType, complexity, screenCount }    │
└────────────────────────────┬────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────┐
│  STEP 3: CONTEXT ENRICHMENT                         │
│  - Inject default design system (theme tokens)      │
│  - Retrieve similar templates via pgvector search   │
│  - Attach component catalog (available components)  │
│  - Inject user's existing project context if edit   │
└────────────────────────────┬────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────┐
│  STEP 4: PROMPT CONSTRUCTION                        │
│  - System prompt: IR schema + component catalog     │
│  - Few-shot examples: 2–3 sample IR outputs         │
│  - User message: enriched prompt                    │
│  - Output constraint: Zod schema enforcement        │
└────────────────────────────┬────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────┐
│  STEP 5: LLM DISPATCH (via BullMQ)                  │
│  - Job enqueued with priority (paid > free tier)    │
│  - Model selection based on complexity score        │
│  - Streaming enabled; tokens emitted via SSE        │
│  - Retry policy: 3 attempts with exponential backoff│
└────────────────────────────┬────────────────────────┘
                             │
                             ▼
                  IR JSON (Zod-validated)
```

#### Model Routing Strategy

| Complexity Score | Model | Avg Latency | Cost |
|---|---|---|---|
| Simple (1–2 screens) | Claude 3 Haiku / GPT-4o-mini | ~3s | Low |
| Medium (3–5 screens) | Claude 3.5 Sonnet | ~8s | Medium |
| Complex (6+ screens, navigation) | Claude 3.5 Sonnet (extended) | ~20s | High |

#### Streaming UX Pattern

```
Client                    Server                  LLM API
  │                          │                        │
  │── POST /generate ────────▶│                        │
  │                          │── enqueue job ─────────▶│
  │◀─ { jobId: "abc" } ──────│                        │
  │                          │                        │
  │── GET /stream/abc ───────▶│                        │
  │   (SSE connection)        │                        │
  │                          │◀─ token stream ─────────│
  │◀─ data: {"progress":10} ─│                        │
  │◀─ data: {"progress":50} ─│                        │
  │◀─ data: {"ir": {...}}   ─│                        │
  │   (SSE closes)            │                        │
```

### 3.2 Code Generation Engine

**Purpose:** Compile a validated IR document into syntactically correct, formatted, production-quality source code for the project's chosen **platform** (React Native or Flutter). Platform is set at project creation and selects the target adapter.

#### Architecture

```
IR Document (JSON)
       │
       ▼
┌─────────────────────────────────────────────┐
│  IR VALIDATOR                               │
│  - Zod schema check                        │
│  - Component reference validation           │
│  - Circular dependency detection            │
└───────────────────┬─────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│  COMPILER PIPELINE                          │
│                                             │
│  IR Node → AST Node (Babel AST format)     │
│                                             │
│  Visitors (one per node type):              │
│  - ViewVisitor → <View style={...}>        │
│  - TextVisitor → <Text style={...}>        │
│  - ImageVisitor → <Image source={...}>     │
│  - ListVisitor → <FlatList data={...}>     │
│  - NavigationVisitor → useNavigation()     │
│  - EventVisitor → onPress={...}            │
└───────────────────┬─────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│  CODE EMITTER                               │
│  - AST → raw code string (@babel/generator) │
│  - Auto-import resolver                     │
│  - Type annotation injector (TypeScript)    │
└───────────────────┬─────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│  POST-PROCESSING                            │
│  - Prettier formatting (consistent style)   │
│  - ESLint auto-fix (no-unused-vars, etc.)   │
│  - package.json generation (dependencies)   │
│  - app.json / metro.config.js generation    │
└───────────────────┬─────────────────────────┘
                    │
                    ▼
         File Tree (TSX files)
         Ready for Sandpack / Export
```

```
├── screens/
```

#### Multi-Platform Compilation (Extensible)

The compiler is **platform-agnostic at the IR level**. The IR describes UI, layout, and behavior; a **target adapter** per platform emits framework-specific code. The project's **platform** is chosen at creation (React Native or Flutter) and determines which adapter runs.

```
IR Document (platform-agnostic)
     │
     ├── ReactNativeAdapter → JSX + StyleSheet + React Native APIs
     ├── FlutterAdapter     → Dart + Widget tree + Flutter APIs
     │
     └── (Future, not implemented)
         ├── KotlinAdapter  → Kotlin + Jetpack Compose
         └── SwiftUIAdapter → Swift + SwiftUI ViewBuilder
```

Design for scale: adding a new platform requires only a new adapter and a new `platform` enum value; IR schema and canvas remain unchanged.

### 3.3 Design Engine

**Purpose:** Provide a pixel-precise drag-and-drop visual UI builder that renders the IR as manipulable components on a canvas.

#### Sub-components

```
┌──────────────────────────────────────────────────────────────────┐
│  DESIGN ENGINE                                                   │
│                                                                  │
│  ┌─────────────────┐  ┌─────────────────┐  ┌──────────────────┐ │
│  │  CANVAS LAYER   │  │  PROPERTIES     │  │  COMPONENT       │ │
│  │                 │  │  PANEL          │  │  LIBRARY         │ │
│  │ - craft.js tree │  │                 │  │                  │ │
│  │ - dnd-kit DnD   │  │ - Style editor  │  │ - 30+ primitives │ │
│  │ - Resize handles│  │ - Prop editor   │  │ - Custom blocks  │ │
│  │ - Selection box │  │ - Event bindings│  │ - Templates      │ │
│  │ - Grid/snap     │  │ - Data bindings │  │ - Drag to canvas │ │
│  └────────┬────────┘  └────────┬────────┘  └──────────────────┘ │
│           │                    │                                 │
│           └────────────────────▼                                 │
│                        IR MUTATION API                           │
│                    (addNode, updateNode,                         │
│                     deleteNode, moveNode,                        │
│                     reparentNode)                                │
└──────────────────────────────────────────────────────────────────┘
```

#### Canvas-to-IR Mutation Flow

Every user interaction on the canvas is translated into a **discrete IR mutation operation**, not a full IR replacement:

```typescript
// Canvas drag event fires:
onDrop(component: DraggedComponent, target: DropZone) {
  irStore.dispatch({
    type: 'ADD_NODE',
    payload: {
      parentId: target.nodeId,
      node: {
        id: generateId(),
        type: component.type,
        props: component.defaultProps,
        style: component.defaultStyle,
      }
    }
  })
  // IR mutation → triggers code compiler → hot-reload preview
}
```

Mutations are:
- **Atomic** — each mutation is a single JSON Patch operation (RFC 6902)
- **Reversible** — stored in an undo/redo stack
- **Collaborative** — broadcast as Yjs operations to other editors

### 3.4 Code Sync Engine (Canvas → Code, One-Way)

**Purpose:** Emit and keep the code editor in sync with the IR whenever the canvas (or prompt) changes. Code edits do **not** sync back to the canvas — the IR is the single source of truth for the visual design.

#### Sync Architecture (One-Way Only)

```
         ┌──────────────────┐
         │   IR (truth)     │  ← Updated by: Canvas, Prompt/LLM
         └────────┬─────────┘
                  │
                  │  IR change → recompile → update code
                  ▼
         ┌──────────────────┐
         │  Code Editor     │  ← Read-only from IR; displays emitted code
         │  (Monaco)        │  ← User can edit for export, but edits don't
         └──────────────────┘    update canvas/IR
```

**Canvas → Code flow:** Canvas mutation (or LLM output) → IR update → Compiler (IR → framework code) → Monaco `setValue()`. No AST parsing or code → IR reconstruction.

#### Collaboration (Canvas-Only)

When multiple users edit the same project, only **canvas/IR mutations** are synced (e.g. via Yjs CRDT). The code editor shows the latest compiled output from the shared IR. There is no conflict between "code edits" and "canvas edits" because code does not write back to the IR.

### 3.5 Preview / Rendering Engine

**Purpose:** Give users an instant, accurate visual representation of the generated app with zero server infrastructure cost.

#### Two-Mode Preview Strategy

```
┌────────────────────────────────────────────────────┐
│  MODE 1: BROWSER PREVIEW (Default, all tiers)      │
│                                                    │
│  Generated Code Files                              │
│         │                                          │
│         ▼                                          │
│  Sandpack Core (WASM Metro bundler)                │
│         │                                          │
│         ▼                                          │
│  React Native Web renderer                         │
│         │                                          │
│         ▼                                          │
│  <iframe> with device chrome (iOS/Android frame)  │
│                                                    │
│  - Hot-reload: <200ms on IR change                 │
│  - Zero server cost                                │
│  - Supports: touch events, scroll, navigation      │
│  - Does NOT support: camera, GPS, native APIs      │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│  MODE 2: NATIVE DEVICE PREVIEW (Premium tier)      │
│                                                    │
│  Generated Code → Expo EAS build (cloud)           │
│         │                                          │
│         ▼                                          │
│  QR code generated                                 │
│         │                                          │
│         ▼                                          │
│  User scans with Expo Go on physical device        │
│                                                    │
│  - True native rendering                           │
│  - Access to all device APIs                       │
│  - Build time: ~2–5 min                            │
└────────────────────────────────────────────────────┘
```

#### Hot-Reload Pipeline

```
IR Change detected (canvas or prompt/LLM)
          │
          ▼  (debounce 150ms)
Compiler Service: IR → updated TSX files
          │
          ▼
Sandpack.updateFiles({ 'screens/Home.tsx': newCode })
          │
          ▼  (Sandpack internal: module graph update)
Preview iframe re-renders changed component only
          │
          ▼
User sees update in ~150–300ms total
```

#### Preview State Persistence

- Current navigation screen is preserved across hot-reloads
- Form input values are preserved
- Scroll position is preserved
- Achieved via Sandpack's module hot-replacement (MHR) — only changed modules are re-evaluated

### 3.6 Project Storage & Versioning

**Purpose:** Persist user work, enable undo/redo, support team collaboration, and provide git-like version history.

#### Storage Architecture

```
┌──────────────────────────────────────────────────────────┐
│  PROJECT STORAGE LAYERS                                  │
│                                                          │
│  L1 — In-Memory (Zustand)                                │
│       Current editing session state                      │
│       Undo/redo stack (last 50 operations)               │
│       Auto-flush to L2 every 30s or on meaningful change │
│                                                          │
│  L2 — PostgreSQL (project_versions table)                │
│       Immutable IR snapshots (content-addressed)         │
│       Each save = new version row                        │
│       Soft-delete (never destroy user data)              │
│                                                          │
│  L3 — S3/R2 (large blobs)                                │
│       Exported code ZIPs                                 │
│       User-uploaded assets (images, fonts, icons)        │
│       Build artifacts                                    │
└──────────────────────────────────────────────────────────┘
```

#### Version Graph

Each project maintains a **DAG of versions** (similar to git commits):

```
v1 (initial generation)
 │
 ├── v2 (user edit A)
 │    │
 │    └── v3 (user edit B)  ← current HEAD
 │
 └── v2b (branch: "dark mode experiment")
```

```sql
CREATE TABLE project_versions (
  id          UUID PRIMARY KEY,
  project_id  UUID REFERENCES projects(id),
  parent_id   UUID REFERENCES project_versions(id), -- null for root
  ir_hash     TEXT NOT NULL,  -- SHA-256 of IR content
  ir_snapshot JSONB NOT NULL, -- full IR document
  created_by  UUID REFERENCES users(id),
  created_at  TIMESTAMPTZ DEFAULT now(),
  message     TEXT,           -- optional user commit message
  is_head     BOOLEAN DEFAULT false
);
```

#### Auto-Save Strategy

```
User activity
     │
     ▼ (debounce: 30s of inactivity OR 100 meaningful mutations)
Create new version snapshot
     │
     ├── If IR hash unchanged → skip (dedup)
     └── If IR hash changed → INSERT new version row
                            → UPDATE project.head_version_id
                            → Async: upload code to R2
```

### 3.7 Project Creation & Platform Selection

**Purpose:** When creating a project, the user selects the **platform** (target runtime). The same IR is used for all platforms; only the code emitter (adapter) changes.

#### Supported platforms (current)

| Platform        | Status   | Emitted stack        |
|----------------|----------|----------------------|
| **React Native** | Supported | TS/JSX, Metro, React Native APIs |
| **Flutter**      | Supported | Dart, Flutter widgets, pubspec   |

#### Future platforms (not implemented)

The IR and adapter pattern are designed so that additional platforms can be added without changing the canvas or IR schema:

| Platform   | Future | Notes                          |
|-----------|--------|---------------------------------|
| **Kotlin** (Android) | Yes    | New adapter: IR → Kotlin + Jetpack Compose |
| **SwiftUI** (iOS)    | Yes    | New adapter: IR → Swift + SwiftUI          |

#### Project creation flow

1. User clicks "New project".
2. User enters name (and optional description).
3. **User selects platform: React Native or Flutter** (required).
4. Backend creates project with `platform` set; all subsequent generation and compilation use the selected platform's adapter.
5. Preview and export use the same platform (e.g. Flutter projects use Dart preview/export).

Platform is **immutable** per project (no switching after creation) to avoid mixed codebases. Users create a new project if they need a different platform.

## 4. Data Flow

### 4.1 Prompt → Code → Preview

**Scenario:** User types "Build a fitness tracking app with a dashboard showing calories, steps, and a workout log."

```
Step 1: USER INPUT
──────────────────
User types prompt in Prompt Panel
→ Frontend validates length & format
→ POST /api/generate { prompt, projectId, options }

Step 2: API GATEWAY
───────────────────
→ JWT verified (Clerk middleware)
→ Rate limit checked: user's generation quota (Redis INCR with TTL)
→ Project ownership verified
→ Request routed to Prompt Service

Step 3: PROMPT SERVICE
──────────────────────
→ Input moderation check (async, fast)
→ Intent classified: appType="fitness", screens=4, complexity="medium"
→ Template search: pgvector finds similar fitness app templates (top-3)
→ Prompt assembled with system prompt + component catalog + few-shots
→ Job enqueued: BullMQ { jobId, userId, prompt, priority }
→ Response: { jobId: "gen_abc123" } returned immediately to client

Step 4: CLIENT STARTS STREAMING
─────────────────────────────────
→ Client opens SSE connection: GET /api/stream/gen_abc123
→ UI shows "Generating your app..." with progress bar

Step 5: LLM WORKER (async)
───────────────────────────
→ Worker picks up job from BullMQ queue
→ Anthropic API called (Claude 3.5 Sonnet, streaming mode)
→ Token stream received
→ Partial IR assembled as tokens arrive
→ Every 10 tokens: emit SSE progress event → client updates progress
→ On completion: full IR string assembled

Step 6: IR VALIDATION
─────────────────────
→ Zod schema validation runs
→ If invalid: retry prompt with error context injected (max 2 retries)
→ If valid: IR saved to project_versions table

Step 7: CODE COMPILATION (async)
─────────────────────────────────
→ Compiler Worker picks up compile job (uses project.platform)
→ IR → platform adapter (React Native or Flutter) → framework-specific AST/code
→ Code emitter → TSX (RN) or Dart (Flutter) file strings
→ Prettier/dart format applied
→ File tree assembled in memory

Step 8: SSE FINAL EVENT
────────────────────────
→ Worker emits: { type: 'complete', ir: {...}, files: {...} }
→ SSE connection closes

Step 9: CLIENT RECEIVES & RENDERS
──────────────────────────────────
→ IR stored in Zustand IR Store
→ Canvas re-renders from new IR (craft.js setState)
→ Code files sent to Sandpack: sandpack.updateFiles(files)
→ Sandpack bundles (WASM, ~1s)
→ Preview iframe hot-reloads
→ User sees rendered app in <3s of final event receipt

Total perceived latency: ~10–25s (LLM dominant factor)
UI feels responsive because of SSE progress streaming
```

### 4.2 Design → Code → Preview (one-way)

**Scenario:** User drags a Button component onto the Home screen canvas and changes its label to "Get Started."

```
Step 1: CANVAS DRAG EVENT
──────────────────────────
User drags "Button" from component library
→ dnd-kit onDrop fires
→ Drop target: HomeScreen, position: after Text node

Step 2: IR MUTATION
────────────────────
→ irStore.dispatch({
    type: 'ADD_NODE',
    payload: {
      parentId: 'screen_home.layout',
      index: 2,
      node: {
        id: 'comp_button_001',
        type: 'Button',
        props: { label: 'Button', variant: 'primary' },
        style: { marginTop: 16 }
      }
    }
  })
→ IR Store updated (in-memory, Zustand)
→ Yjs doc updated (for collaboration broadcast)

Step 3: CANVAS RE-RENDER
─────────────────────────
→ craft.js tree re-renders with new Button node
→ Button appears on canvas immediately (optimistic, ~16ms)

Step 4: CODE EMIT (Design → Code, one-way)
───────────────────────────────────────────
→ IR mutation triggers compile pipeline (debounced 150ms)
→ Compiler: only the modified screen (HomeScreen.tsx) recompiled
→ Monaco editor receives: setValue(newHomeScreenCode)
→ Code editor shows the new <Button label="Button" ... /> line

Step 5: PREVIEW HOT-RELOAD
───────────────────────────
→ Sandpack.updateFiles({ 'screens/HomeScreen.tsx': updatedCode })
→ Sandpack module graph: only HomeScreen module invalidated
→ Preview iframe hot-reloads HomeScreen component
→ Button appears in preview (~150ms after canvas drop)

Step 6: USER EDITS LABEL VIA PROPERTIES PANEL
───────────────────────────────────────────────
→ User clicks Button on canvas → Properties Panel shows
→ User changes "label" prop from "Button" to "Get Started"
→ irStore.dispatch({ type: 'UPDATE_PROP', nodeId: 'comp_button_001',
                     prop: 'label', value: 'Get Started' })

Step 7: REPEAT EMIT CYCLE
──────────────────────────
→ IR updated → Code recompiled → Monaco updated → Sandpack hot-reloads
→ Preview shows "Get Started" button in ~150ms

Step 8: PERSISTENCE
────────────────────
→ After 30s idle or 100 mutations:
→ POST /api/projects/:id/save { ir: currentIR }
→ New version row inserted in project_versions
→ Auto-versioned, no explicit user action needed

Note: Direct edits in the code editor (Monaco) are not synced back to the IR
or canvas. The code view is the emitted output; users can copy or export it.
Changes to the design must be made on the canvas (or via prompt).
```

## 7. Scalability Strategy

### Horizontal Scaling Plan

```
               Load Balancer (Cloudflare / ALB)
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
    API Server 1    API Server 2    API Server 3
    (stateless)     (stateless)     (stateless)
          │               │               │
          └───────────────┼───────────────┘
                          │
                  ┌───────┴────────┐
                  ▼                ▼
            LLM Worker       LLM Worker
             Pool (N)         Pool (N)
                  │
                  ▼
              Redis (BullMQ)
                  │
                  ▼
            PostgreSQL
          (read replicas)
```

### Scaling Each Component Independently

| Component | Scaling Approach | Bottleneck Signal |
|---|---|---|
| **API Servers** | Horizontal (stateless, add instances) | CPU > 70% or p99 latency > 500ms |
| **LLM Workers** | Horizontal (add workers, same BullMQ) | Queue depth > 50 jobs |
| **Compiler Workers** | Horizontal | Queue depth > 20 jobs |
| **PostgreSQL** | Read replicas (Neon branching) | Read IOPS saturation |
| **Redis** | Redis Cluster (shard by key prefix) | Memory > 80% |
| **Preview (Sandpack)** | No scaling needed — runs in client | N/A |

### Database Scaling Progression

```
Phase 1 (0–10K users):
  Single PostgreSQL instance (Neon/Supabase managed)
  All queries on primary

Phase 2 (10K–100K users):
  Add 1 read replica
  Route: reads → replica, writes → primary
  Add pgvector index tuning

Phase 3 (100K+ users):
  Connection pooling: PgBouncer (max 20 actual connections per server)
  Read replicas per region (US, EU, APAC)
  Hot IR snapshots → Redis cache (TTL 5min)
  Archive old versions to cold storage (S3) after 90 days
```

### Caching Layers

```
L1 — Client-side (React Query):
     - Project list: stale 30s
     - Project IR: stale 5s (aggressive for live editing)
     - User profile: stale 5min

L2 — Redis (server-side):
     - Rate limit counters: TTL = end of day
     - Session tokens: TTL = 24h
     - Compiled code for unchanged IRs: TTL = 10min
       (cache key = SHA-256(ir_snapshot))
     - Component catalog (rarely changes): TTL = 1h

L3 — CDN (Cloudflare):
     - Static assets (JS, CSS, fonts): immutable with hash
     - Exported ZIP files: 24h TTL
     - Component template thumbnails: 7-day TTL
```

### Queue Prioritization

LLM jobs use BullMQ's priority system to avoid paid users being blocked by free tier:

```
Priority 1 (highest) — Enterprise plan users
Priority 2           — Pro plan users
Priority 3           — Free tier users
Priority 4 (lowest)  — Background jobs (exports, analytics)
```

## 8. Performance Optimization Techniques

### Frontend Performance

| Technique | Target | Implementation |
|---|---|---|
| **Code splitting** | Initial JS bundle size | Next.js dynamic imports for Monaco, Sandpack, craft.js |
| **Monaco lazy load** | Editor load time | Load Monaco only when code editor tab is activated |
| **Sandpack lazy init** | Preview startup | Initialize Sandpack after first generation completes |
| **IR partial updates** | Canvas re-render | Only re-render IR nodes that changed (React reconciliation + nodeId keys) |
| **Debounced compile** | Canvas → code emit | 150ms debounce on IR change before recompiling and updating Monaco |
| **Virtual canvas** | Large app performance | Only render canvas nodes that are in the viewport |
| **Web Workers** | Compilation | Run IR → code compilation in a Web Worker to avoid blocking main thread |

### Backend Performance

| Technique | Target | Implementation |
|---|---|---|
| **IR compilation cache** | Repeat compile latency | Redis cache keyed by SHA-256(ir_snapshot); TTL 10min |
| **Incremental compilation** | Code sync latency | Only recompile screens whose IR nodes changed |
| **LLM prompt caching** | Token cost + latency | Anthropic prompt caching for static system prompt prefix |
| **Streaming responses** | Perceived generation latency | SSE streaming so UI updates during generation |
| **DB query optimization** | Project load latency | Single JOIN query for project + head_version; no N+1 |
| **Connection pooling** | DB connection overhead | PgBouncer with transaction-mode pooling |
| **Async asset processing** | Upload experience | Images resized/optimized in background worker post-upload |

### LLM Cost Optimization

| Technique | Savings | Description |
|---|---|---|
| **Prompt caching** | ~40% | Cache static system prompt prefix (Anthropic beta feature) |
| **Model routing** | ~60% | Route simple prompts to cheaper models |
| **IR diff prompting** | ~70% | For edits, only send the changed screen + delta prompt |
| **Template retrieval** | Reduces hallucination | Provide relevant templates → fewer retry calls |
| **Token budget limits** | Hard cost cap | Set max_tokens per generation based on plan |

## 9. Security Considerations

### Authentication & Authorization

```
Every API request flow:
  1. JWT extracted from Authorization header
  2. Clerk SDK verifies JWT (public key, no DB hit)
  3. userId extracted from JWT claims
  4. Resource ownership check (projectId must belong to userId or user's org)
  5. Plan-based feature flag check
  6. Rate limit check (Redis)
```

### Authorization Model (RBAC)

| Role | Read Project | Edit Project | Invite Members | Billing | Delete Project |
|---|---|---|---|---|---|
| **Org Owner** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **Org Admin** | ✅ | ✅ | ✅ | ❌ | ✅ |
| **Member** | ✅ | ✅ | ❌ | ❌ | ❌ |
| **Viewer** | ✅ | ❌ | ❌ | ❌ | ❌ |
| **Personal user** | ✅ | ✅ | N/A | ✅ | ✅ |

### LLM Security

| Threat | Mitigation |
|---|---|
| **Prompt injection** | Never include user-provided content in system prompt; user prompt is always in the `user` role |
| **Data exfiltration via prompt** | System prompt includes explicit "Do not include personal data in output" instruction |
| **Malicious code generation** | Generated code runs in Sandpack iframe sandbox (no DOM access, no network in sandbox) |
| **Excessive token usage** | Hard `max_tokens` limit per request; plan-based daily token budget |

### Preview Sandbox Security

The Sandpack preview iframe is sandboxed with strict Content Security Policy:

```html
<iframe
  sandbox="allow-scripts"
  csp="
    default-src 'none';
    script-src 'self' 'unsafe-eval';
    style-src 'self' 'unsafe-inline';
    img-src data: blob: https:;
    connect-src 'none';
  "
/>
```

- `connect-src: 'none'` — Preview code cannot make network requests
- `allow-scripts` only — No `allow-same-origin`, no `allow-forms`, no `allow-popups`
- Generated code cannot access cookies, localStorage, or parent window

### Data Security

| Layer | Control |
|---|---|
| **Transport** | TLS 1.3 everywhere; HSTS preloaded |
| **Database** | Encrypted at rest (Neon/Supabase managed); column-level encryption for API keys |
| **IR data isolation** | Row-level Security (RLS) in PostgreSQL — users can only SELECT/UPDATE their own rows |
| **API keys** | Stored as `sha256(key)` in DB; full key shown only once at creation |
| **Asset uploads** | Presigned S3/R2 URLs with 15min expiry; server validates MIME type before accepting |
| **Secrets** | Doppler for all environment variables; never in source code or Docker images |

### PostgreSQL Row-Level Security

```sql
-- Users can only access their own projects
ALTER TABLE projects ENABLE ROW LEVEL SECURITY;

CREATE POLICY projects_isolation ON projects
  USING (
    owner_id = auth.uid()
    OR org_id IN (
      SELECT org_id FROM org_members WHERE user_id = auth.uid()
    )
  );

-- Versions inherit project access
CREATE POLICY versions_isolation ON project_versions
  USING (
    project_id IN (SELECT id FROM projects)  -- inherits projects RLS
  );
```

### Input Validation & Injection Prevention

- All inputs validated with Zod before reaching service layer
- IR schema strictly validated — no executable code paths in IR
- Parameterized queries only — no string concatenation in SQL
- Generated filenames sanitized (no path traversal: `../`)
- Asset uploads: virus scanning via ClamAV in background worker

## 10. Multi-Tenant System Design

### Tenancy Model: Shared Database, Isolated Data

The platform uses a **shared database, shared schema** model with Row-Level Security providing logical isolation. This is optimal for SaaS at this scale because:

- No per-tenant DB provisioning complexity
- Full data isolation enforced at DB level (not application level)
- Cross-tenant queries impossible by default
- Cost-effective until 10M+ rows per tenant

### Tenant Hierarchy

```
Platform
    │
    ├── Personal Users (no org — treated as org of one)
    │
    └── Organizations
         ├── Owner (1)
         ├── Admins (N)
         ├── Members (N)
         └── Viewers (N)
              │
              └── Shared Projects, Component Libraries, Billing
```

### Data Isolation Architecture

```
All DB queries:
  SELECT * FROM projects
  WHERE owner_id = $userId          ← Personal projects
     OR org_id IN (                 ← Org projects user belongs to
       SELECT org_id FROM org_members
       WHERE user_id = $userId
     )

PostgreSQL RLS enforces this at the DB driver level —
even if application code has a bug, cross-tenant leaks are impossible.
```

```
              ├── User in EU → Route to EU cluster (Frankfurt)
              ├── User in US → Route to US cluster (Virginia)
              └── User in APAC → Route to APAC cluster (Singapore)

Each region:
  - Dedicated PostgreSQL primary + replicas
  - Dedicated Redis cluster
  - Dedicated LLM worker pool
  - Shared S3 with region-affinity (eu-central-1 for EU)

Data never crosses region boundaries for enterprise tenants.
```

## Summary: HLD Decision Matrix

| Concern | Decision | Rationale |
|---|---|---|
| **State management** | IR as single source of truth | Decouples canvas and code; one-way sync (canvas → code) only |
| **LLM output format** | IR JSON via Zod schema | Eliminates unpredictable raw code generation |
| **Preview architecture** | Client-side Sandpack | Zero server cost, infinite scale, <200ms hot-reload |
| **Tenancy model** | Shared DB + RLS | Cost-effective, DB-enforced isolation, no provisioning overhead |
| **Async model** | BullMQ job queue | LLM calls are slow; queue prevents HTTP timeouts and enables priority |
| **Code sync direction** | One-way (IR → code) | Canvas/prompt update IR; code is emitted from IR only; no code → canvas |
| **Service architecture** | Modular monolith → extract | Move fast now; extract LLM worker first when scale demands |
| **Auth** | Clerk + JWT + RLS | Zero-trust: JWT verified at gateway, RLS enforced at DB |
| **Collaboration** | Yjs CRDT | Operational transform is too complex; CRDT handles offline/concurrent edits |
| **Versioning** | Immutable IR snapshots | Append-only history; no data loss, cheap storage with dedup via hash |
| **Platform** | Chosen at project creation | React Native or Flutter; IR platform-agnostic; future: Kotlin, SwiftUI via new adapters |
